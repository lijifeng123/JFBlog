# iOS 稳定性与性能优化：防崩溃、启动与列表实战总结

> 本文围绕 iOS 稳定性与性能优化展开，拆解 UGCrash 的异常拦截与上报机制，梳理 Instruments 的常用工具，并总结 App 启动、列表滑动和复杂视觉效果的优化思路。

## 一、项目中的防崩溃机制

项目采用 **UGCrash 主动防护 + Bugly、Firebase Crashlytics、Sentry 采集上报** 的组合方案。真正降低部分闪退概率的是 UGCrash，第三方平台主要负责异常和崩溃数据收集。

### 1. Method Swizzling 与异常捕获

UGCrash 通过 Category 和 Method Swizzling 交换数组、字典、字符串及 KVC 的相关方法，在包装方法中使用 `@try/@catch` 调用原实现并捕获 `NSException`。

以可变数组插入为例，方法交换后，`insertObject:atIndex:` 实际先进入防护方法。如果插入 `nil` 或索引越界，系统异常会被捕获，本次插入被忽略，同时记录错误并进入上报流程。

不同场景采用的恢复策略包括：

- 数组读取越界：返回 `nil`；
- 数组插入 `nil`、插入或删除越界：忽略本次操作；
- 字典包含非法键值：忽略操作或过滤非法数据；
- 字符串截取越界：返回 `nil`；
- KVC 赋值异常：忽略本次赋值。

需要明确：**防崩溃不代表修复业务错误。** 它只是把“立即崩溃”降级为“本次操作失败”。如果调用方认为数据已经插入，后续仍可能出现数据缺失、页面状态异常等问题。

### 2. 未识别方法的消息转发兜底

针对 `unrecognized selector sent to instance`，项目交换了 `forwardingTargetForSelector:`。

当对象没有实现目标方法，并且自身没有自定义消息转发时，防护逻辑会动态创建一个兜底类，为该类添加缺失的方法，再将消息转发给兜底对象。方法返回默认值，从而避免继续触发未识别方法崩溃。

这里有两个细节：

- 方法不是补到原对象上，而是补到动态创建的兜底类上；
- 当前这条链路主要使用 `NSLog` 记录，没有进入统一的 `UGCrashNotification` 上报流程。

### 3. UIView 主线程保护

项目还交换了 `setNeedsLayout`、`layoutIfNeeded`、`layoutSubviews` 和 `setNeedsUpdateConstraints`。如果调用发生在子线程，就通过 `dispatch_async` 切换到主线程执行，降低 UIKit 非主线程调用带来的风险。

### 4. 异常采集与上报

UGCrash 捕获异常后，会收集异常名称、原因、调用栈和默认恢复策略，并发送 `UGCrashNotification`：

- 国内版通过 Bugly 上报非致命异常；
- Firebase 版本通过 Crashlytics 记录错误；
- Bugly、Firebase 和 Sentry 自身还负责真正未捕获崩溃的采集。

UGCrash 主要防护被显式 Hook 的 Objective-C `NSException`，无法防止野指针、非法内存访问、C/C++ 异常、死锁、栈溢出和 Watchdog 强杀等所有问题。

## 二、Instruments 常用工具怎么选

Instruments 是一组性能分析模板。日常业务开发中，最常用的通常是以下三个：

| 工具 | 主要用途 |
| --- | --- |
| Time Profiler | 定位 CPU 占用高、主线程耗时和页面卡顿 |
| Allocations | 分析对象分配、内存增长和常驻对象 |
| Leaks | 检测内存泄漏和循环引用 |

其他常见工具包括：

- **App Launch**：分析启动阶段；
- **Hangs**：定位主线程无响应；
- **System Trace**：分析线程调度、锁等待和系统调用；
- **Core Animation**：分析帧率与渲染性能；
- **Zombies**：辅助定位已释放对象被访问；
- **VM Tracker**：分析虚拟内存构成；
- **Energy Log**：分析耗电和后台活动。

使用时尽量选择真机、Release 包和真实业务数据。先复现问题，再在时间轴上选中异常区间，过滤自己的工程代码。不要凭感觉优化，也不要只使用一次 Debug 启动数据作为结论。

## 三、App 启动速度优化

启动优化的核心不是把所有任务都丢到子线程，而是：**缩短从进程创建到首屏展示、用户可以操作的关键路径。**

### 1. 按阶段分析启动

- **pre-main**：动态库加载、符号链接、ObjC Runtime 初始化和 `+load`；
- **didFinishLaunching**：Crash、日志、数据库、推送和业务 SDK 初始化；
- **首屏阶段**：RootVC 创建、布局、图片加载和首屏数据准备。

可以使用 App Launch、Time Profiler 和 `os_signpost` 建立启动基线，线上再结合 MetricKit、Xcode Organizer 观察真实用户数据。

### 2. 减少启动关键任务

将启动任务分为四类：

1. **启动必需**：Crash 采集、基础运行环境、Window 和 RootVC；
2. **可后台执行**：独立配置读取、非首屏数据解析、日志整理；
3. **首屏后执行**：非关键统计、非首屏业务模块和预加载；
4. **按需初始化**：二三级页面或首次使用才需要的 SDK 与资源。

同时减少 `+load` 中的耗时操作，避免主线程同步网络、文件 I/O、数据库迁移、大 JSON 解析和大图解码。

### 3. 让首屏尽快展示

- 创建轻量 RootVC，简化首屏布局；
- 优先展示本地缓存，网络返回后局部刷新；
- 图片按显示尺寸加载和解码；
- 非首屏页面与资源懒加载；
- 控制后台初始化并发，避免线程和 CPU 抢占。

不能为了缩短 `didFinishLaunching` 时间，就一次性向全局队列提交大量任务，也不能延迟 Crash SDK 或破坏初始化任务之间的依赖关系。

## 四、列表滑动优化

列表优化可以概括为：**主线程少做事、Cell 尽量轻、图片按需处理、布局提前算好、滚动任务可取消、数据局部更新。**

### 1. Cell 复用与布局

- 正确使用复用标识，避免重复创建相同子视图；
- 复用时重置文本、图片、选中状态和异步任务；
- 不在 `cellForRow` 中读取文件、查询数据库或解析大 JSON；
- 固定高度直接返回，动态高度按内容、宽度和字体缓存；
- 减少无必要的视图层级、约束和频繁 `layoutIfNeeded`。

### 2. 图片下载、解码与缓存

图片通常是列表卡顿的重点。建议完整落实以下流程：

1. 后台下载；
2. 按 Cell 显示尺寸缩放和解码；
3. 使用内存与磁盘缓存；
4. 回到主线程设置图片；
5. Cell 复用时取消旧请求；
6. 设置图片前确认 Cell 仍对应原数据。

避免在主线程处理原图，也避免 Cell 复用后旧请求回写导致图片串位。

### 3. 预取、数据处理与局部刷新

- 使用 `UITableViewDataSourcePrefetching` 或 `UICollectionViewDataSourcePrefetching` 提前准备下一页数据和图片；
- 对不再需要的预取任务进行取消或降级；
- 提前完成 Model 转 ViewModel、格式化、排序和高度计算；
- 使用 Diffable Data Source 或局部更新，避免高频全量 `reloadData`；
- 限制下载与解析并发，避免快速滑动时任务占满 CPU、网络和内存。

## 五、保留圆角、阴影等效果的渲染优化

复杂视觉效果不一定要删除，关键是避免在列表滑动时每帧重复计算。

### 1. 预渲染静态效果

对于固定圆角背景、渐变、标签、徽章和阴影，可以提前使用 `UIGraphicsImageRenderer` 绘制成 `UIImage`，供多个 Cell 共享。缓存 key 应考虑尺寸、颜色、圆角、屏幕 scale 和深色模式。

圆角图片则可以在后台按显示尺寸缩放、裁剪并缓存，不再依赖每个 Cell 重复设置裁剪。

### 2. 使用 Layer 栅格化

`shouldRasterize` 可以让系统把 Layer 及其子层缓存为位图，并通过 `rasterizationScale` 保证清晰度。

它适合局部复杂但内容不变的视图，不适合频繁变化的整个 Cell。内容或尺寸变化会使缓存失效，无脑开启反而可能增加渲染与内存成本。

### 3. 按效果选择方案

- 固定圆角背景：预渲染共享图片；
- 固定阴影：预渲染，动态阴影至少设置 `shadowPath`；
- 静态模糊：截图、模糊一次并缓存；
- 实时模糊：缩小区域或降低更新频率；
- 重复渐变：简单渐变不一定慢，实测存在瓶颈后再缓存成图片。

预渲染与栅格化都需要平衡内存开销，最终应通过 Core Animation 和 Time Profiler 对比优化前后的真实数据。

## 六、总结

iOS 稳定性与性能优化不是单点技巧，而是一套完整的方法：

- 防崩溃框架负责降低部分异常的影响，但不能代替正确的业务代码；
- Instruments 负责量化问题，优化必须建立在真实测量之上；
- 启动优化聚焦首屏可交互关键路径；
- 列表优化聚焦每一帧的 CPU、GPU 和内存成本；
- 预渲染、栅格化和缓存用于减少重复工作，而不是简单牺牲视觉效果。

真正有效的优化流程始终是：**测量、定位、调整、验证，并持续关注线上数据。**
